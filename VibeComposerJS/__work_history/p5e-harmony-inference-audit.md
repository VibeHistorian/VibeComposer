# P5e: block Melody harmony inference audit

Audit completed 2026-10-11 against current production Java and TypeScript sources. At this checkpoint alternate progression generation, selection and shared voicing flattening were not implemented in TypeScript. The following proposal and baseline are historical audit evidence; the subsequent [P5e implementation record](p5e-harmony-integration-record.md) documents their delivered behavior and validation.

## Production source and execution order

Java source links below are relative to the current [generation package](../../midimasterpiece/src/main/java/org/vibehistorian/vibecomposer/generation/).

1. [MidiGenerator.initializeArrangementProgressions](../../midimasterpiece/src/main/java/org/vibehistorian/vibecomposer/generation/MidiGenerator.java) performs an empty Melody pass using the **first configured Melody part**, base harmony, seed offset zero and a fresh Section before arranging the song. Arrangement presence does not choose this source. Imported user Melody takes a separate branch, reserved for P11.
2. [MelodyBlockSkeletonGenerator.prepareSkeletonGeneration / assembleChordNotes / publishSkeletonResults](../../midimasterpiece/src/main/java/org/vibehistorian/vibecomposer/generation/MelodyBlockSkeletonGenerator.java) fills `chordMelodyMap1` only while it is empty, with seed offset zero and matching root/generated-name counts. It records the first repetition (`o == 0`) of each chord's **skeleton notes**, after block selection/pitch exceptions and any skeleton embellishment. Publication precedes `MelodyExpansion.convertMelodySkeletonToFullMelody`, tonal/chord/avoid repair, pause handling, phrase swing, mode/key conversion and phrase-level custom MIDI replacement.
3. [MelodyChordInference.getChordsFromMelodyPitches](../../midimasterpiece/src/main/java/org/vibehistorian/vibecomposer/generation/MelodyChordInference.java) weights pitch classes by **rhythm value**, not sounding duration or velocity: each note contributes once per eighth-note increment until the current chord duration is filled. It retains the four most frequent classes, then calls `MidiUtils.applyChordFreqMap` with match rank **2** and `baseFreqMap` (C, Dm, Em, F, G, Am, Bdim). This is inference in Java's internal C/Ionian coordinate system, before final key/scale conversion.
4. `populateMelodyBasedProgression` replaces interior chords only: `start = 1`, `end = chordCount - 1`. It preserves the original first and last root/voicing arrays, maps inferred interior chords to independent root arrays and voices the entire alternate progression through ordinary `squishChordProgression`. `alternateChords` gets the original endpoint names. Imported-source inference uses rank 1, the larger `freqMap`, all chord slots and its own segmentation; do not fold it into this block path.
5. [SectionGenerationPlanner.shouldUseMelodyProgression](../../midimasterpiece/src/main/java/org/vibehistorian/vibecomposer/generation/SectionGenerationPlanner.java) and `MidiGenerator` select the alternate root/voicing arrays for **Swap Chords** (section variation index 1). With no custom section progression, the alternate-name string must be nonempty. When section chords/durations were replaced, Java instead checks root-count equality plus the variation flag and restores the base duration list. This can override an explicit section progression; it conflicts with the translation's independent-override contract and must be treated as a deliberate translation difference, not reproduced silently.
6. `MidiGenerator.fillMelodyPartsForSection` has an additional **Swap Melody** branch (variation index 2): use alternate harmony for Melody alone when **Skip N-1 chord** (index 0) is off and section chords were not replaced. Index 2 also shifts the skeleton seed by 100. These are separate decisions; one all-role alternate toggle does not implement both. [Section.sectionVariationNames](../../midimasterpiece/src/main/java/org/vibehistorian/vibecomposer/Section.java) is the exact variation lookup.

## Harmony voicing consumer

[ChordGUI.saveChordGenSettings / loadChordGenSettings](../../midimasterpiece/src/main/java/org/vibehistorian/vibecomposer/gui/ChordGUI.java) maps `randomChordVoicingChance` to [ChordGenSettings.flattenVoicingChance](../../midimasterpiece/src/main/java/org/vibehistorian/vibecomposer/Panels/ChordGenSettings.java), default **100%**. Its consumers are global progression preparation, section custom progression preparation and alternate Melody progression preparation. It is a **project harmony setting**, not a Chords track-reroll rule and not the per-part close/open voicing choice.

[MidiUtils.squishChordProgression / squishChordProgressionProgressively / calculateAverageNote](../../midimasterpiece/src/main/java/org/vibehistorian/vibecomposer/MidiUtils.java) define its musical behavior:

- Start a dedicated `Random` with the full project seed. Explicit custom inversion slots skip both adjustment and the random draw.
- Average all chord pitches with Java's `0.001` denominator offset; ignored inversion slots contribute root arrays. Ordinary squish uses that fixed average; progressive squish starts with the first chord, then recomputes from the processed prefix.
- Draw once per eligible chord even at 0% or when a large chord will not be squished. If the draw succeeds and the chord has at most three tones or `spiceFlattenBigChords` is enabled, raise its first tone by 12 when more than six semitones below the average, lower its last tone by 12 when more than six above, then sort.
- Inference always uses **ordinary** squish, even when the global progressive option is enabled. Its inversion skip list is empty, including the preserved endpoints. Thus preserved endpoint names/root arrays do not guarantee unchanged endpoint voicings.

Bass consumes roots; Chords and Arpeggio consume voiced chords; Melody has separate root/repair consumers. Root arrays must remain independent of flattened voicings. Exact matching requires routing both arrays through the shared context rather than deriving one from the other.

## Current translation and missing integration

| Area | Existing behavior | Required work |
| --- | --- | --- |
| Block generator | [generateMelody](../frontend/src/app/core/music/melody-generator.ts) builds `byChord`, expands/repairs it and publishes a later pre-swing onset map | Publish a separate immutable skeleton pitch/rhythm map before expansion; preserve random consumption and existing phrase output |
| Melody dependency context | [sectionMelodyContext](../frontend/src/app/core/music/phrase.ts) resolves first-Melody section patches and uses manual replacements for onset dependencies | Keep this map separate from base-harmony inference; it has no rhythm values and represents a later stage |
| Harmony | [harmony.ts](../frontend/src/app/core/music/harmony.ts) maps Chordlets/root/spice/inversion independently per chord | Add progression-wide voicing settings and distinct roots/voicings; current Chordlet fixtures do not cover flattening |
| Arrangement | Sections store degree overrides and part patches; no Swap Chords/Swap Melody selection exists | Add typed section harmony selection and explicit precedence, preserving custom section harmony and sparse part patches |
| Shared output | Playback, score, overview and MIDI use `layOutTrackPhrase` | Resolve the same effective harmony there and in dependency generation; prevent alternate-harmony inference feeding back into itself |
| Timing | Every chord is one four-beat bar; MIDI has one project tempo | P5f owns variable durations and scheduling; equal-duration inference can be implemented first without claiming custom-duration parity |

The onset callback is unsuitable as an inference shortcut: it discards rhythm values, follows repaired/paused/manual notes, includes section patches and key/scale conversion, and can change with swing-adjacent timing or dependency settings that did not drive Java's original inference. Likewise, sounding `PhraseNote.durationBeats` cannot substitute for the skeleton rhythm value.

## Implementation contract and control placement

The following is the audit's implementation proposal; these controls remain unavailable until their consumers are implemented and validated.

1. Add a pure inference helper and a separate skeleton publication result. Infer once from the first generated Melody track's **base settings and base harmony**; use its existing deterministic track-seed policy and document that policy as a translation difference from Java panel order offsets. Use the project seed separately for progression voicing. Keep source IDs explicit; missing/disabled source produces an unavailable result, with no fallback to another track's pending edit.
2. Manual `editedPhrase`, including an empty replacement, retains ownership of audible notes and existing onset dependencies. It is not an imported source and must not be used to infer new chords. A hidden generated skeleton may provide alternate-harmony metadata without replacing manual notes; the UI must identify its generated source. Clearing a manual replacement remains the existing explicit action.
3. Introduce project harmony settings for **Flatten voicing %** (0..100, default 100), **Flatten large chords**, and **Progressive voicing** in the detailed harmony inspector. Do not place them in Melody/Chords part patches or track-reroll headers. Flattening must affect all applicable global/section/alternate harmony consumers before its control is active.
4. Add separate section inspector choices for using inferred harmony across pitched roles and for Melody alone. Preserve explicit section chords/durations ahead of inferred selection, preserve first/last names/roots, and report unavailable sources. Do not mutate `customChords` or a user's Chordlets as display metadata. Any automatic selection chances belong with arrangement policy, apart from the realized section choice.
5. Share typed root/voicing/selection context with P5f; retain current track-base → section-role → section-track part resolution. Cache derived results by immutable project/context identity, without history entries or stored generated arrays. Store only validated settings, choices and any explicit source reference; history/JSON/session restoration must replay exactly.

Tie ordering needs an explicit oracle before implementation. `createChordFreqMap` returns a Java `HashMap`, and note-frequency ties also originate in a `HashMap`; sorting is stable over those iteration orders, not the documented major-chord list. `applyChordFreqMap` ranks five candidates, can prefer the circle successor among best matches, and otherwise selects the second candidate. Fixtures must capture production iteration/tie behavior rather than replace it with an invented musical preference. Cover empty/rest-only maps and one/two-chord progressions separately: Java's endpoint loops can duplicate the one-chord entry in the inferred root/voicing arrays. Recover safely with unchanged short progressions and document that recovery rather than asserting parity with malformed Java output.

## Validation and remaining acceptance

Validation on 2026-10-11: `npm run test:parts` **176/176 passed**, and `npm run test:playback` **21/21 passed**. Existing checks cover supported complete seeded block phrases, Chordlet mappings, section-degree precedence, independent sparse overrides, manual replacements, history, JSON/session replay and parsed MIDI. Source inspection confirms playback, score, overview and MIDI share `layOutTrackPhrase`.

These passes establish the existing pipeline's baseline, **not alternate-progression or flattening parity**. No production browser review was required for this source/document audit; no UI changed.

Implementation acceptance still requires production Java fixtures for skeleton maps, duration weighting, tie/circle decisions, preserved endpoints, root independence, flatten draws/skipped inversions, ordinary/progressive/large-chord cases and complete alternate-section phrases. Include exact long seeds and missing/disabled/manual sources; verify distinct section choices, explicit harmony precedence, part overrides, undo/redo, malformed imports, session replay and matching score/playback/MIDI. P5f extends that matrix to unequal durations and section key/tempo changes; P11 covers imported-source inference. Existing complete Melody fixtures do not establish any of these missing behaviors.
